# Observed first-cycle weaknesses and revision

The first primary output contains 2,850 whitespace-delimited words; the contrast contains 2,986. Both are actual ChatGPT responses, preserved without rewriting their judgments. The initial tests distinguish Low internal-support exposure from provisional Moderate service-firm exposure and properly retain uncertainty; they are not represented as wholesale failures.

W01 Usability: the long outputs repeat definitions and investigation details, obscuring the bounded classification and making integration harder. Revision adds an 800-1100-word target and a field-specific allocation.

W02 Reproducibility: primary application_finding says "potential incremental business-process innovation with a potentially substantial change" and keeps workflow breakthrough as an alternative. This is defensible but does not present status, type, magnitude and novelty consistently as separate dimensions. Initial criteria say applied value without an explicit implementation gate, though the model supplies the missing OECD distinction. Revision makes the implementation/commercialization status explicit in instructions, uses a named baseline, and requires evidence to distinguish a qualitatively new mechanism from improved existing work. The diagnosis is a weakness in specification and presentation, not an allegation that the model falsely claimed implementation.

W03 Grade boundaries: first outputs withhold High/Existential absent evidence, but initial instructions provide only broad labels. Revision specifies dependence, substitution and adaptive options, and allows withholding a grade when economics are missing. It separates governance consequence from business-model exposure and requires a non-disruption counter-case. This strengthens the rule; it is not empirical calibration of a score.

Cases, source register, application and decision horizon are unchanged between cycles. Only specialist rules and metadata version change. First-cycle prompt packets preserve original configuration. Borderline-case review and second-cycle observations will be recorded in records/test_and_revision_log.md. No failure is manufactured and no output is altered to create a desired grade.

W04 Borderline output: cycle_1/contrast_2_response.json recognizes that the screenshot-only demo does not establish source access or autonomous tool use, yet assigns "Moderate, conditional and low-confidence" based on what a future validated agent could do. It also fills several organizational details with "likely" baselines despite missing economics. This is the informative ambiguous/weak case. A conditional scenario is useful, but it can be mistaken for a grade of the evidenced demo. Version 0.2 explicitly requires scope validation, no invented economics, and withholding a definitive grade or clearly separating conditional branches when those inputs are absent. Retesting will check whether the model keeps desired workflow potential separate from actual demo evidence.
